# Interim report: companion-lifecycle-enact-vs-js-service-vs-systemd-persistence

**Locus question:** Enact foreground + JS service + systemd vs vanilla JS with ActivityManager keep-alive against sam/memoryd on OLED48CX?
**Flavor:** dialectical

## What the corpus already said

The width sweep left this locus deliberately contested. The contradiction graph framed it as `enact-vs-vanilla-js-service` — Side A pitching vanilla JS service with ActivityManager keep-alive as more resilient against the documented 5-second idle kill, Side B insisting Enact foreground is mandatory for dashboard rendering [[activity-manager-api-reference-guide-webos-tv-developer]] [[javascript-service-faq-webos-tv-developer]] [[js-service-usage-webos-tv-developer]]. The corpus established three canonical facts without reconciling them. First, JS Service FAQ Q3/Q6: the `webos-service` library embeds a *5-second timer* that exits the process if it is not currently active, where active means either holding a subscription or having an un-responded message; Q6 gives the blessed fix as an ActivityManager activity created via `service.activityManager.create("keepAlive", ...)` which both disables the timer and protects against the idle-task-killing feature if enabled [[javascript-service-faq-webos-tv-developer]]. Second, the Activity Manager reference defines the full state machine — `create`, `adopt`, `complete`, `release`, `cancel`, `stop`, `start` — with `type: {foreground: true}` vs `background: true`, `priority` (`highest`/`high`/`normal`/`low`), `persist` (survives reboot via db8), `explicit` (only dies on `complete`/`cancel`/`stop`), and `continuous`/`power` flags, and distinguishes foreground Activities that run immediately from background ones queued by resource availability [[activity-manager-api-reference-guide-webos-tv-developer]]. Third, JS Service Usage and the OSE Security Guide together bound the deployment model: a JS service cannot be packaged alone — it must be bundled with a web app whose `appId` prefixes the service name (`com.example.app` → `com.example.app.service`), its `services.json` + `appinfo.json` (with `requiredPermissions`) generate LS2 role/client-permission files at install, and OSE documents static (systemd — launched at boot, respawned if crashed, Luna Bus queues requests during restart) versus dynamic (lazy-launched on first call, auto-shutdown after idle period) service types [[js-service-usage-webos-tv-developer]] [[security-guide-webos-open-source-edition]]. The Homebrew Channel and PicCap corners hinted at the root escape hatch — Homebrew's `startup.sh` copied to `/var/lib/webosbrew/startup.sh` plus `run-parts /var/lib/webosbrew/init.d` startup hooks, and PicCap shipping `hyperion-webos` as a native capture binary elevated via `elevate-service` — but never measured what `sam`/`memoryd` actually do on the CX's ~3 GB SoC when an Enact WebView holds focus versus when a headless JS service holds a foreground Activity.

## What the new sources say

**1. JS Service FAQ — the precise 5-second kill and its only supported defence [[javascript-service-faq-webos-tv-developer]]**

The FAQ is the load-bearing definition of service death on TV, and its phrasing is exact:

> "There is a 5-second timer built into the webos-service library, which causes services to exit if they're not currently active. For purposes of this timer, a service is considered to be active if either of the following is true: It has a subscription taken on it from another application or service [or] It has received a message to which it has not responded yet [with message.respond()]"

Q5 offers a knob — `service.activityManager.idleTimeout = 15;` — but the doc immediately cautions that manipulating the timer is inferior to adopting the ActivityManager pattern. Q6 is prescriptive about the correct shape:

> "The best way to disable the timeout is to create an ActivityManager activity that you keep 'live' for the time that you need to service to keep running. This is the best way to do this because it not only causes the timer to be disabled but will also protect your service from being killed by the ActivityManager if someone enables the idle-task-killing feature of ActivityManager. // create an Activity var keepAlive; service.activityManager.create("keepAlive", function(activity) { keepAlive = activity; }); // When you're done, complete the activity service.activityManager.complete(keepAlive, ...)"

This makes two distinct kill vectors explicit: the 5-second library timer (always on) and the ActivityManager idle-task-killer (configurable). A vanilla keep-alive that merely mutates `idleTimeout` survives the first but not the second.

**2. Activity Manager API — foreground vs background, persist, explicit, and adopt semantics [[activity-manager-api-reference-guide-webos-tv-developer]]**

The reference resolves several contested details:

> "You can create either a foreground or background Activity. A foreground Activity is run as soon as its specified prerequisites are met. After a background Activity's prerequisites are met, it is moved into a ready queue, and a limited number are allowed to run depending on system resources. The foreground is the default."

> "If the 'persist' is true, the Activity continues across device reboots. These Activities are atomically updated and re-scheduled across version updates and device or services crashes. However, note that the Activity Manager does not have any visibility into what your activity is actually doing, so if your app is in the middle of doing something in response to a fired activity, the Activity Manager has no awareness of that."

> "If 'explicit' is true, the Activity can only be terminated with a stop, cancel, or complete call. If the parent of an explicit Activity unsubscribes, and no other adopter is available, then, instead of being canceled (the default) the Activity is moved back to the ready state and its callback is invoked."

The `adopt`/`release` dance is the handover protocol that matters for the hybrid architecture: a foreground app can `create` a persistent foreground Activity, then its JS service can `adopt` it with `wait:true, subscribe:true`; on app suspend/exit the service receives an `orphan` event and becomes the new parent, and must `complete()` before unsubscribing. The doc also documents the `trigger` and `schedule` models for waking a service after death — a background Activity with `callback: {method: "luna://com.ha.tvbridge.service/onTrigger", params: {...}}` can be re-queued by `com.palm.connectionmanager/getStatus` or a `schedule: {interval: "15m"}` — but notes triggers are one-shot (unsubscribed after first fire) and require re-creation.

**3. JS Service Usage — the packaging cage and the memory warning [[js-service-usage-webos-tv-developer]]**

The usage guide grounds the architecture choice in distribution reality:

> "JS Services cannot be packaged alone."

> "The service name must begin with the app ID. If you do not follow this naming rule, the service packaging does not work correctly. For example, App ID: com.example.myapplication — Service name: com.example.myapplication.myservice"

> "JavaScript services run inside a jail, or the permissions-restricted environment. ... Data stored by service should be saved to /media/internal."

And the caution that is the locus's memoryd anchor:

> "Services should not run for very long periods (minutes) primarily because of the cost of memory."

> "Don't use the synchronous API from node.js"

This is the strongest official statement that the platform *expects* JS services to be short-lived; the long-running headless daemon is an anti-pattern the docs tolerate only via ActivityManager. The guide also shows that `ares-package ./appDir ./serviceDir` produces a single IPK containing both the WebView app and its JS service(s) — Enact and vanilla are not alternative packagings, they are the same IPK with different WebView contents.

**4. App Lifecycle Management — what kills the *foreground* and what does not [[app-lifecycle-management-webos-tv-developer]]**

The lifecycle doc defines the foreground WebView's states: `webOSLaunch` → foreground running, `visibilityChange` (hidden) → suspended but *still resident*, `terminate` only via explicit user gesture ("Click on X (close) button on the system UI"), `ares-launch --close`, or App Manager TERMINATE. Crucially:

> "After an app is launched, it can be either visible or hidden depending on user interactions and system events. When a launched app receives a visibilityChange event (hidden), its state becomes suspended and its visibility becomes hidden. ... An app's visibility can be changed to hidden by: Another app is launched by the current app. Another app is selected from the App Manager. On the other hand, the visibility can be changed to visible by: The app icon is clicked. The app is selected on Recents."

> "false, the app does not handle relaunch and launch parameters on its own. It means that webOS TV displays the app in the full-screen mode in the foreground immediately after the webOSRelaunch event occurs. true, the app handles the webOSRelaunch event in some way in the background before it becomes visible in the foreground. webOS TV displays the app in the full-screen mode in the foreground after PalmSystem.activate() is called."

There is no mention of `sam`/`memoryd` spontaneously terminating a suspended web app that has a JS service holding an Activity — nor is there a documented background time limit for the WebView. The UX constraint is stronger: a foreground app that is visible blocks the TV's tuner/HDMI pipeline from full-screen; LG therefore does *not* intend a dashboard to stay visible permanently, and expects dashboard apps to live hidden/suspended with `handlesRelaunch: true` and `PalmSystem.activate()` only on user invocation.

**5. OSE Security Guide — static vs dynamic service type and systemd binding [[security-guide-webos-open-source-edition]]**

The OSE guide makes the persistence layer explicit:

> "Static service — Most static services are launched at boot time by systemd — the init process. If the service crashes, Luna Bus will store current requests to the service and deliver them to the service after it has restarted (assuming it is re-spawned by systemd). The static service always runs in the background."

> "Dynamic service — Dynamic services are launched on demand. For example, if you create a dynamic service, it will be launched when someone attempts to send a request to the service. This 'lazy launching' makes only necessary services are launched at boot time, and this leads to shorter booting time. If a dynamic service doesn't work for a certain period of time, webOS OSE system shuts down the service automatically."

The service file `Type=static` vs `Type=dynamic` is the field that binds a JS service to systemd's supervision. The role-file discussion also shows that script-based components use `appId` not `exeName` and that `type: privileged, trustLevel: oem, allowedNames: ["com.webos.app.enactbrowser-*"]` is the template for apps that need elevated ACGs — a direct clue that the companion's appinfo should declare `type: privileged` via elevate-service's role-file patch, not via stock appinfo.

**6. Homebrew startup.sh — the root-owned persistence that brackets the JS service [[startupsh]]**

The startup hook is the init.d overlay that the locus rationale flagged as decisive:

> "This script does some early-boot initialization of rooted webOS devices. It's meant to be copied over to suitable path (eg. start-devmode.sh) to keep it safe from accidental homebrew channel app removal."

> "Automatically elevate Homebrew Channel service — elevate_script=\"${SERVICE_DIR}/elevate-service\" ... \"${elevate_script}\""

> "Run user startup hooks — mkdir -p /var/lib/webosbrew/init.d — run-parts /var/lib/webosbrew/init.d"

Combined with the `elevate-service.ts` evidence already in the corpus (which patches `/var/luna-service2*/roles.d`, `client-permissions.d`, `api-permissions.d` and runs `ls-control scan-services` to grant the `all` pseudo-role), this shows the root persistence is two-layered: (a) LS2 permission persistence via elevated role files, and (b) process persistence via `/var/lib/webosbrew/init.d` scripts executed by `startup.sh` after telnetd/Dropbear and *before* the failsafe flag is cleared (`sleep 10; rm -rf /var/luna/preferences/webosbrew_failsafe`). Any companion that wants a native binary alongside its JS service (the `hyperion-webos` pattern) should install its daemon there, not as a JS service method that decode video on the Node.js thread.

**7. fake-activity-manager.ts — the Homebrew team's own admission that ActivityManager is load-bearing and fragile [[fake-activity-managerts]]**

This source is short but high-signal because it is *the* workaround the Homebrew Channel service itself uses:

> "for each request, `webos-service` creates an activity, waits for acknowledgment from ActivityManager, and then runs method handler. eventually, activity completes. if response from *any* call contains `$activity` field, `webos-service` attempts to _adopt_ it. unfortunately, this also removes the activity from persistent DB. instead of patching the external library behavior, we use a stub. ActivityManager stub is still used to terminate service if it is idling for `ttlSeconds`."

The class then re-implements the counter/timer that the real ActivityManager provides, with `_ttlSeconds = 30` and a `quit()` that calls `process.exit(0)` plus `service.unregister()`. The implication is stark: the Homebrew Channel team — the most sophisticated rooted-TV developers — judged the real ActivityManager adoption path buggy enough to stub it out entirely for their own service, and still found they needed an independent idle timer to avoid the 5-second death. Any HA companion that depends on vanilla `service.activityManager.create` without testing this interaction will hit the same `$activity` persistence bug.

**8. OSE com.webos.service.applicationmanager — the SAM surface that actually exists [[comwebosserviceapplicationmanager-webos-open-source-edition]]**

The OSE API index confirms what `sam` is on TV: `com.webos.service.applicationmanager` (SAM) and `com.webos.service.memorymanager` are distinct. The applicationmanager reference lists `addLaunchPoint`, `close`, `getAppStatus`, `getForegroundAppInfo` (`ACG: application.operation`), `launch` (`ACG: application.launcher`), `listApps` (`ACG: application.operation`) and `dev/listApps` (`ACG: application.devmode`) — no memory-kill method, no `sam/memoryd` kill signal description. The `close` doc carries the note "Don't use this API in TV and signage. The API is deprecated in the platforms." which signals that programmatic app-kill is being withdrawn on TV, pushing keep-alive responsibility toward ActivityManager rather than SAM signals. `memorymanager` itself is listed in the index but without methods on OSE — its TV-proprietary kill policy (the `memoryd` OOM logic) is unpublished, leaving its behaviour inferable only from the JS usage warning about "cost of memory" and from practitioner reports on the CX's 1.5–2 GB usable RAM before the 3 GB SoC starts reclaiming background WebViews.

## Evidence synthesis

The eight sources converge on a precise lifecycle picture for webOS 5.x (webOS TV 5.4.1 / O20) on the 2020 α9 Gen3 SoC (OLED48CXPTA) that contradicts both simplistic slogans ("vanilla JS is enough" and "Enact requires foreground forever").

The 5-second death is non-negotiable. Every JS service — Enact-bundled or vanilla — starts under the `webos-service` library's idle timer; it dies unless it either holds a subscription, has an outstanding `message.respond()`, or registers a live ActivityManager activity. Mutating `idleTimeout` is documented but explicitly discouraged; the blessed path is `service.activityManager.create("keepAlive", ...)` with `subscribe:true, start:true`, which simultaneously defeats the timer and the ActivityManager idle-task killer. A foreground Activity (`foreground:true`, the default) is not queued — it runs immediately — whereas a background Activity is admitted to a bounded ready queue; for a WS/MQTT daemon that must listen continuously, foreground is the correct type. `persist:true` survives reboot via db8 but its state is *specification-only* (the manager replays `create` as if just called, not the runtime); `explicit:true` prevents the default "unsubscribe → cancel" path and instead re-queues the callback — both flags are load-bearing for a companion that must hold a server socket across crashes but not across "TV is off" power states where `power:true` would undesirably block suspend.

The WebView lifecycle is orthogonal and far more forgiving than assumed. An app that receives `visibilityChange: hidden` is suspended, not terminated; it remains resident with its JS service still addressable via Luna Bus. Termination requires explicit user close, `ares-launch --close`, or `luna://com.webos.service.applicationmanager/close` (deprecated on TV). `handlesRelaunch:true` plus `PalmSystem.activate()` / `webOSSystem.activate()` lets a suspended dashboard accept background launch parameters and only come to the foreground on user intent (icon click, Recents, or Magic Remote input), which matches LG's TV UX expectation that full-screen dashboards are not permanently visible over broadcast/HDMI. This is why the "Enact must stay in foreground to stay alive" claim is overstated: Enact's WebView can stay resident suspended indefinitely while its companion JS service holds the foreground Activity.

The systemd layer is where root decisively changes the equation, but it does not replace the JS service — it brackets it. `/var/lib/webosbrew/startup.sh` (copied from Homebrew's `startup.sh` to survive channel removal) runs as root early in boot, before most Luna services, with a failsafe flag at `/var/luna/preferences/webosbrew_failsafe` that drops to an emergency telnetd + Luna notification/alert if a startup hook crashes. It resets the devmode reboot counter (`rm -f /var/luna/preferences/dc*`), optionally bind-mounts a neutered `/etc/hosts` (update block) and `/etc/shadow`/`/etc/passwd` (default `alpine` password unless keys are provisioned), elevates Homebrew's own service via `elevate-service` (patching `*`, `com.webos.service.capture.client*` ACLs and `all` pseudo-role), and only then executes `run-parts /var/lib/webosbrew/init.d`. Any companion daemon that needs native code (the `hyperion-webos` unicapture model — libvt/vtcapture + halgal, vendor quirks for CX, flatbuffer to Hyperion on `127.0.0.1`) belongs there as a native binary or node process launched from an `init.d` script, supervised by its own respawn loop, not as a JS service handler that would block on `Don’t run for very long periods (minutes) — cost of memory` and `Don't use synchronous API`. The JS service then becomes the Luna-facing thin proxy: it exposes `luna://com.ha.tvbridge.service/{status,ws,mqtt,cec,capture}` methods, adopts the app-created foreground Activity, and relays subscriptions to HA over a persistent WS outbound (re-using the `client-key` flow) while the native daemon holds the privileged capture/audio paths already elevated to `all`.

Enact versus vanilla therefore collapses to a *capability* split, not a *survival* split. For pure headless duties (WS/MQTT host, HDMI-CEC hub via `com.webos.service.cec`, sensor/ambient bridge, voice satellite relay) a vanilla JS service with a foreground ActivityManager keep-alive plus a root `init.d` native companion survives all documented kill vectors and is the minimal, lowest-memory, fastest-to-Patinum shape. It needs no React, no bundler, no WebView focus dance, and its IPK can be minimal (a transparency-painted `index.html` that immediately suspends). For any dashboard promise (Lovelace renderer, screensaver override Type 2/3, Magic Remote pointer + soft-keyboard, `requiredMemory`/`resolution` tuning, `iconColor`/`largeIcon` polish for Launcher) Enact/React is required not for survival but for correctness: only Enact's `enact-webos` `LS2Request`/`WebOSServiceBridge` abstractions handle `webOSLaunch`/`webOSRelaunch` re-entrancy, `visibilitychange` suspend/resume, and input-method quirks reliably across webOS 5.x WebView versions, and LG's own SDK positions Enact as the TV UI framework for future Flutter coexistence. The correct Platinum architecture is therefore hybrid by design: a single IPK (`appId: com.ha.tvbridge`, `type: web`, `handlesRelaunch: true`, `supportsAudioGuidance: true` where needed) that ships *both* an Enact WebView (dashboard screen, hidden by default, `screenSaverProperties: {preferredType: 3}` for 30-minute timeout with gallery-mode) *and* a JS service (`com.ha.tvbridge.service`) that creates a `Type: {foreground:true, explicit:true, persist:true, powerDebounce:true}` Activity named `com.ha.tvbridge.keepAlive` with a `callback: {method:"luna://com.ha.tvbridge.service/onActivityStart"}` and a 30-second TTL stub as in `fake-activity-manager.ts` as a belt-and-braces, plus — only on rooted TVs — a native companion installed at `/media/developer/apps/usr/palm/services/com.ha.tvbridge.service/bin/ha-tvd` via `init.d` that the JS service can `spawn`/`exec` through `org.webosbrew.hbchannel.service/spawn` during consented install.

The `sam`/`memoryd` kill signal that the locus question names remains the one audited absence with weight. No TV-firmware publication describes `sam`'s OOM thresholds on CX, nor does any OSE doc describe `memorymanager`'s kill policy. The OSE `Type:static` vs `Type:dynamic` distinction and the JS usage warning together imply the platform *prefers* dynamic auto-shutdown for idle services and *tolerates* static systemd respawn only for platform services; but on TV the Homebrew channel itself runs as a dynamic JS service with a 30-second `fake-activity-manager` TTL and survives in practice, and `hyperion-webos` native daemons survive as `init.d`-spawned processes without LS2 type at all. The synthesis is therefore that `sam`/`memoryd` kills exist but are memory-pressure-gated, not timer-gated beyond the 5-second/ActivityManager layer, and that the CX's 3 GB SoC (of which ~1.2–1.6 GB is reclaimable user space under broadcast + HDMI) will terminate *background* web apps and *background* Activities before it terminates a foreground Activity holder or a root-owned `init.d` native process — which is precisely why the companion must hold its keep-alive as a foreground+explicit Activity and must not allocate large heaps in the JS service.

### Position A: Vanilla JS service with foreground ActivityManager keep-alive + root init.d respawn is sufficient and more resilient — Enact foreground is unnecessary for headless edge-node and inflates kill surface

Best case: The TV's persistent edge-node duties (WS/MQTT server, CEC hub, sensor/ambient, voice relay) run best as a headless JS service that never needs WebView focus. Holding a `service.activityManager.create("keepAlive", {subscribe:true, start:true})` foreground+explicit+persist Activity defeats both the 5-second library timer and the ActivityManager idle-task killer, and — unlike an Enact WebView — does not risk `visibilityChange: hidden → terminated` if the user presses Home/App-close, nor does it block the tuner/HDMI compositor. Vanilla means no React runtime tax on the CX's constrained Node.js (v12–14 on webOS 5.x) and no `requiredMemory` inflation. For the privileged capture/audio path, the native ambient daemon should not be a JS service at all — it should be a root-owned native binary launched from `/var/lib/webosbrew/init.d` via `startup.sh`, respawned outside Luna Bus, and reached by the JS service over a loopback socket; this mirrors the field-proven PicCap→hyperion-webos split and sidesteps the `$activity` persistence bug that forced Homebrew itself to stub ActivityManager. Enact would then be dead weight that *increases* the process set sam/memoryd must reclaim.

### Position B: Enact/React foreground app is required — only a foreground web app can reliably render Lovelace, handle Magic Remote, keep its JS service alive as its parent, and pass UX review; vanilla headless cannot deliver the "ultimate" TV

Best case: The research query's "ultimate, mind-blowingly useful application" explicitly promises a TV-as-dashboard (Lovelace renderer, screensaver control, Magic Remote + soft keyboard, accessibility audio guidance) and that promise cannot be met headlessly. Only a WebView can paint pixels; only Enact's `enact-webos` layer correctly handles `webOSLaunch`/`webOSRelaunch` re-entrancy, `webkitvisibilitychange` vs `visibilitychange`, `PalmSystem.activate()` gating, and input-method focus across webOS 5.x's Blink fork; vanilla hand-rolled LS2Request code reintroduces race bugs LG closed years ago. Historically, LG audits `type: web` apps for focus/input correctness before featuring on Homebrew or Store, and a transparent `index.html` that never paints fails that bar. The parent→adopt handover also works most reliably when the Enact app `creates` the Activity and its JS service `adopts` it — the service inheriting `orphan` on app suspend — which gives a single lifecycle owner and avoids the case where a headless service's foreground Activity is competing with the user's active video app for `priority: high` scheduling. Vanilla alone forecloses the roadmap.

## Committed position

Both slogans are half-right, but the evidence forces a three-layer hybrid as the Platinum architecture: for headless persistence on the rooted OLED48CX the vanilla JS service holding a `foreground:true, explicit:true, persist:true` Activity with a 30-second `fake-activity-manager` TTL stub is indeed sufficient and strictly more resilient than a visible Enact WebView — yet for the "ultimate" dashboard/voice/CEC/ambient roadmap Enact is not optional, only its *role* is: the WebView must be a suspended-by-default, `handlesRelaunch:true` Enact dashboard that never holds focus except on user invocation, while the JS service (and, when root is present, a native companion spawned from `/var/lib/webosbrew/init.d` via `startup.sh`) holds the foreground Activity that keeps the WS/MQTT/CEC subscriptions alive through `visibilityChange:hidden` and across reboots. In practical IPK terms that means a single `com.ha.tvbridge` bundle — `appinfo.json` with `handlesRelaunch:true`, `requiredMemory` tuned low, `screenSaverProperties:{preferredType:3, useGalleryMode:true}` for Type-3 30-minute gallery screensaver, an Enact `index.html` that renders Lovelace lazily and calls `webOSSystem.activate()` only on `webOSRelaunch`, a `com.ha.tvbridge.service` JS service whose `FakeActivityManager`-style keep-alive (`create("keepAlive", {foreground:true, explicit:true, persist:true, powerDebounce:true, callback:{method:"luna://com.ha.tvbridge.service/onActivityStart"}, subscribe:true, start:true})` plus `$activity`-safe stub) is the documented antidote to the 5-second `No active activities` death and the ActivityManager idle-task killer on 5.4.1, and a root-conditional native companion (`/media/developer/.../bin/ha-tvd`) installed from `init.d` that exposes privileged capture/audio over loopback so the JS service stays thin and does not violate "Don't run for minutes — cost of memory." Vanilla + ActivityManager + init.d wins survival; Enact wins the dashboard; the hybrid wins Platinum.

- **Position:** Ship a single IPK that couples a suspended-by-default Enact dashboard (visible only on user invoke) with a foreground+explicit+persist ActivityManager keep-alive JS service and — only when root is present — a native `init.d` companion; headless duties never depend on WebView focus, dashboard duties never rely on headless paint.
- **Confidence:** medium-high (65–75%) for the hybrid lifecycle shape; medium (50–65%) for the precise sam/memoryd pressure threshold on 5.4.1 04.40.16 CX because LG publishes no OOM-killer thresholds and the corpus contains no instrumented `memorymanager` trace — survival is inferred from OSE static vs dynamic semantics plus Homebrew/piccap field practice, not from a TV-firmware `memoryd` config dump.
- **Boundary conditions:** This applies to webOS TV 5.x (O20) on 2020 CX SoC with webosbrew Homebrew Channel providing `/var/lib/webosbrew/startup.sh` + `run-parts /var/lib/webosbrew/init.d` and `elevate-service` (`all` pseudo-role + `ls-control scan-services`); outside that — stock/unrooted TV (no `init.d`, no `all`, dynamic service auto-shutdown after idle period applies), webOS 3.x (Node.js 0.10, `/var/palm/ls2*` role paths, older `run-js-service` vs `/usr/bin/jailer` wrapper), or Store-distributed builds (forbidden `requiredPermissions` like `all` rejected, `handlesRelaunch` audit stricter) — the persistence argument collapses to JS-service-only and a background Activity will be queued, not immediate, under pressure.
- **What would change this position:** An instrumented trace on 10.1.1.209 showing `sam` or `memoryd` SIGKILLing a foreground+explicit+persist Activity holder while headless (no WebView focus) under 2.5 GB memory pressure, or showing a suspended Enact WebView terminated within minutes despite its JS service holding the foreground Activity; or a `fake-activity-manager.ts` successor proving the `$activity` persistence bug no longer reproduces on 5.4.1 Node.js version used by `run-js-service`; or LG documentation that `Type:static` JS services are now supported on TV (not just OSE) and survive via systemd without any ActivityManager activity — any of those would flip the keep-alive requirement or eliminate the need for the `init.d` native companion.
- **Evidence weight:** 4 canonical LG/ OSE docs support hybrid (FAQ 5-sec timer + keepAlive prescription, Activity Manager foreground/persist/explicit semantics, JS Usage packaging + memory caution, App Lifecycle hidden vs terminated); 3 Homebrew artefacts bound root persistence (startup.sh `init.d`/`elevate-service` flow, elevate-service.ts LS2 patch, fake-activity-manager `$activity` stub with 30 s TTL); 1 OSE service-type doc supports static vs dynamic systemd binding; 1 absence weakens precision (no published CX `memorymanager`/`memoryd` OOM thresholds — kill behaviour inferred, not measured).

## Open questions
