# Interim report: ultimate-edge-node-cec-ambient-voice-dashboard-soc-limits

**Locus question:** Which edge-node feats (CEC hub, ambient capture, voice satellite, Lovelace dashboard) are feasible under CX SoC/memory and need elevated native binaries?
**Flavor:** convergent

## What the corpus already said

The width sweep banked the raw primitives but left their SoC-cost reconciliation for this locus. On CEC, the OSE `com.webos.service.cec` doc proved a split that matters for root-requirement: `getConfig / listAdapters / scan` are `ACG: cec.query` while `setConfig / sendCommand` are `ACG: cec.operation` [[comwebosservicecec-webos-open-source-edition]] — both `dev`-tier and therefore reachable via `requiredPermissions` without root, unlike TV-proprietary PQ/eim methods that carry `private` + `oem`. On ambient, `hyperion-webos` established that capture is not a JS-service method but a rooted native binary with four backends — `libdile_vt` (3.x+) / `libvtcapture` (5.x+) for video and `libgm` (3.x+) / `libhalgal` (5.x+) for UI, kept separate by `unicapture` and blended only if desired — plus a quirk bitmask (`QUIRK_DILE_VT_CREATE_EX 0x1`, `QUIRK_DILE_VT_NO_FREEZE_CAPTURE 0x2`, `QUIRK_ALTERNATIVE_DUMP_LOCATION* 0x4-0x40`, `QUIRK_VTCAPTURE_FORCE_CAPTURE 0x100`) [[github-webosbrewhyperion-webos-hyperionng-video-grabber-for-webos-github]]. `PicCap` then supplied the load-bearing AI conflict: `"Since the 'AI Picture Pro', 'AI Brightness', 'AI Genre Selection', 'AI Image Game Optimizer' and 'AI Game Sound' options use the same recording process as Hyperion WebOS, dropouts may occur during recording. Consequently, a live preview in HyperHDR is temporarily unavailable"` [[github-tbsnillerpiccap-piccap-hyperion-sender-app-ambilight-for-lg-webos-tvs-git]]. On lifecycle, the JS Service FAQ's 5-second timer — `"There is a 5-second timer built into the webos-service library, which causes services to exit if they're not currently active"` — and its blessed defence `service.activityManager.create("keepAlive", ...)` [[javascript-service-faq-webos-tv-developer]] together with the App Lifecycle doc's `visibilityChange hidden → suspended` (not terminated, termination only via `X close` / `ares-launch --close`) [[app-lifecycle-management-webos-tv-developer]] framed the keep-alive puzzle, but left `memoryd` OOM thresholds, UMI audio routing, and voice-satellite realism unaudited — the gaps this locus closes.

## What the new sources say

**1. Memory Manager — the published OOM policy and hard numbers [[comwebosservicememorymanager-webos-open-source-edition]]**

The OSE doc is the only canonical quantified statement of LG's kill policy:

> "Manages applications to ensure that the system does not run into kernel-Out-Of-Memory situation. This is achieved by killing applications that are in the background when we reach low memory conditions."

It then gives concrete thresholds in the `getMemoryStatus` example that contradict folk assumptions of single-digit-megabyte margins:

> `"system": {"level": "normal","available": 5995,"total": 7538}, "threshold": {"low": {"enter": 250,"exit": 280}, "critical": {"enter": 100,"exit": 130}}`

and a `requireMemory` hint — `"Requests for the memory that is required to launch an application. Note: This method is called by the SAM module when it is about to launch an application."` with `requiredMemory: 120` as the worked example — plus `getManagerEvent` subscription `"killing: application killing event when memory level is under 'low'"` that reports `{"id":"com.webos.app.test.enact","instanceId":"...","type":"killing"}` when a background Enact app is reaped. The `sysInfo` dump further partitions `Essential: BSP 669224 K / Kernel 508892 K / System PSS 750928 K`, `Foreground PSS: 90490 K`, `Performance: Cached Kernel 304672 K`, and `Free: 5550936 K`, and shows per-app PSS in `PSS View` (e.g., `surface-manager-daemon 43910 K`, `webapp-mgr 5957 K`, foreground Enact `~30 MB`). The ACG split is also signal: `getMemoryStatus / getManagerEvent` are `memorymanager.query` (dev-reachable) while `requireMemory` is `memorymanager.management` (management-tier, likely oem on TV). This grounds the CX SoC analysis: background WebViews are killed first when `available` dips below 250 MB, foreground Activity holders survive until `critical 100 MB`, and the companion must declare a modest `requiredMemory` and stay thin.

**2. AI Voice service — why the TV cannot be a drop-in Assist satellite via OSE voice [[comwebosserviceaivoice-webos-open-source-edition]]**

The OSE `com.webos.service.ai.voice` reference demolishes the naive "just call luna://com.webos.service.ai.voice" voice-satellite plan. Its `start`/`stop` are gated `ACG: ai.management` with the note `"This method is only for allowed clients."`, while `getResponse`/`getState` are `ACG: ai.voice`:

> `start — ACG: ai.management — "Starts the service based on the mode selected. Note: This method is only for allowed clients." Parameters: mode: "continuous" | "single", keywordDetect: true | false`
> `getResponse — ACG: ai.voice — "Returns speech recognition results. This method is asynchronous."` subscribable with provider always `"googleassistant"` in the OSE example

The state machine `idle → waitActivation → recording → thinking → answering` and the Google Assistant setup ritual (`/etc/googleAssistant/client_secret.json`, `./get_credentials.sh`, `/etc/systemd/system.conf.d/ai.conf` with `GOOGLEAI_DEVICE_MODEL`, `systemctl restart ai`) are OSE-only; no TV ThinQ counterpart is documented, and `keywordDetect: true` defaults to Snowboy `KITT` model at `/etc/googleAssistant` with model swap via `KEYWORD_DETECT_MODEL` in `/var/systemd/system/env/ai.env`. On the CX (webOS TV 5.x O20), the actual TV voice path is ThinQ via Magic Remote BT mic, not Google Assistant, so this OSE service either does not exist or is not wired to the TV's mic DSP — `start` would 401 without `all` role even if present. The implication is architectural: do not wrap `com.webos.service.ai.voice`; build a parallel native ALSA capture + Wyoming streamer that bypasses it entirely, and treat `ai.management` as root-only if ever probed on 10.1.1.209.

**3. Camera2 — USB-only reality that bounds the "camera/ambient" pillar [[comwebosservicecamera2-webos-open-source-edition]]**

The camera service note is succinct and load-bearing for the "TV as camera" hype:

> "Provides an interface to capture and stream images from a camera that is connected to a webOS device. Note: Currently, only V4L2 USB cameras are supported."

It lists `getCameraList` as `ACG: camera.query` (returns `{"deviceList":[{"id":"camera1"}]}` or `[]` if none, subscribable) and `capture`/`close`/`open`/`startPreview` etc. as `ACG: camera.operation` (17 methods, all `camera.operation` except `getCameraList`). The handle lifecycle is explicit: `open` → `startPreview(handle)` → `capture(handle, nimage 1-30, path /tmp/Picture*.jpeg)` → `close(handle)`, with live preview streamed to SystemV/POSIX shared memory for GStreamer consumers. The CX has no built-in camera; the only way to get `deviceList` non-empty is to plug a UVC USB camera into the TV's USB port. That reframes "camera/ambient" from "TV watches the room by itself" to "TV can be a camera host if the user supplies hardware" — a niche but Platinum-documentable sensor entity (image capture interval, DBus-shared preview). Without USB hardware, this pillar is limited to HDMI capture (unicapture), not room camera.

**4. Wyoming protocol — the minimal local voice plumbing HA actually ships [[wyoming-protocol-home-assistant]]**

The HA docs reduce voice satellite to a protocol, not a cloud:

> "The Wyoming integration connects external voice services to Home Assistant using a small protocol. This enables Assist to use a variety of local speech-to-text, text-to-speech, and wake-word-detection systems, such as: Speech-to-Phrase, Whisper, Piper, openWakeWord"

Its `iot_class is Local Push` and it supports auto-discovery — a Wyoming satellite announces itself and HA shows `Discovered`. Configuration is either passive (mDNS/broker discovery) or manual `Add Integration → Wyoming Protocol → host:port`. The note that `9% of active installations` already run it signals Platinum reviewers will expect Wyoming over any bespoke `ai.voice` wrapper. For the TV, this means the voice daemon does not need to run Whisper/Piper on-SoC (which would crush the α9); it only needs to ship 16 kHz PCM over Wyoming to HA where Whisper/Piper/openWakeWord run on the HA host. The companion's job is audio capture + Wyoming client, not inference.

**5. Assist pipelines — the WebSocket contract a satellite must speak [[assist-pipelines-home-assistant-developer-docs]]**

The developer doc gives the exact streaming contract that replaces `com.webos.service.ai.voice/getResponse`:

> "The Assist pipeline integration runs the common steps of a voice assistant: Wake word detection, Speech to text, Intent recognition, Text to speech. Pipelines are run via a WebSocket API: {\"type\": \"assist_pipeline/run\", \"start_stage\": \"stt\", \"end_stage\": \"tts\", \"input\": {\"sample_rate\": 16000}}"

It defines stages `wake_word → stt → intent → tts`, events `run-start`, `wake_word-start/end`, `stt-start`, `stt-vad-start/end`, `stt-end`, `intent-start/end`, `tts-start/end`, and the binary streaming rule: `"After starting a pipeline with stt as the first stage ... speech data can be sent over the WebSocket connection as binary data. Audio should be sent as soon as it is available, with each chunk prefixed with a byte for the stt_binary_handler_id. ... To indicate the end ..., send a binary message containing a single byte with the stt_binary_handler_id."` plus audio-enhancement knobs `noise_suppression_level 0-4`, `auto_gain_dbfs 0-31`, `volume_multiplier 1.0-2.0` (recommended `2 / 31 / 2.0` for quiet mics). This is the spec a TV-native voice daemon must target: open HA WebSocket, `assist_pipeline/run` with `start_stage stt`, stream PCM16 16 kHz with handler-prefix bytes, handle `stt-vad` events, and play back `tts_output.url` audio via `com.webos.service.audio` or raw ALSA. It also confirms the SIP-like efficiency — no need to buffer full utterances on TV, chunked streaming with VAD timeout (continually reset when VAD detects speech) is native.

**6. App Resources + implicitly appinfo — dashboard packaging constraints [[app-resources-webos-tv-developer]]**

The TV SDK resource guide enforces packaging discipline that bounds the Lovelace dashboard:

> "Do not count on the TV device's Internet connectivity for core functionalities of your app, and keep frequently-accessed assets local to the app - in other words, package them with the app, rather than load them every time they are needed"

and pathing `"The path to each asset should be specified relative to the index.html file. For example, it will look like assets/my_image.png, not start with /media/developer/."` plus required chrome: `icon 80×80 PNG`, `largeIcon 130×130 PNG`, `splashBackground 1920×1080 PNG`, `iconColor HEX`, `title ≤20 chars`, `appDescription ≤60 chars`. Read with the app-lifecycle note that `background` and `splashBackground` images are `required` and that Enact is LG's TV UI framework (with Flutter now co-supported), this locks the dashboard to a bundled, offline-first Enact WebView that renders Lovelace from cached Lovelace JSON plus WS state, not a remote URL that fails when TV is offline during boot. It also confirms the IPK must carry `icon`/`largeIcon` at exactly those pixel sizes or LG/Homebrew review rejects — the companion's launcher tile cannot be a generic placeholder if it wants "Platinum-quality native" polish.

## Evidence synthesis

The six new sources plus the corpus converge on a tiered feasibility map where SoC/memory and the AI Picture conflict are the gating facts, not Luna ACLs alone.

*CEC hub is the clean win and needs no elevated binary.* The OSE `cec` methods are all `dev`-tier (`cec.query` / `cec.operation`); declaring `"requiredPermissions": ["cec.query","cec.operation"]` in `appinfo.json` and installing via dev-mode sideload already makes `luna://com.webos.service.cec/scan` and `luna://com.webos.service.cec/sendCommand` reachable from the JS service, which can then bridge HA's `hdmi_cec` integration semantics over WS. The TV's physical address is `0.0.0.0` (TV), so HA `hdmi_cec:` device maps like `TV: 0.0.0.0`, `Pi Zero: 1.0.0.0` etc. can be driven by proxying `sendCommand` payloads (`report-audio-status`, `report-power-status`, `set-volume`, `one-touch-play`, `system-information`). No `/var/lib/webosbrew/init.d` daemon is required; the JS service's `foreground:true, explicit:true, persist:true` Activity keeps the proxy alive through `visibilityChange:hidden`. This is the only edge-node feat that is stock-feasible, low-memory (CEC scan is a single hub round-trip, ~1 KB JSON), and Platinum-documentable without root warnings — it should be the first entity cluster shipped.

*Ambient capture is the mind-blowing feat but is gated on three simultaneous conditions: root, native binary, and AI Picture off.* `hyperion-webos` field practice shows the CX on webOS 5.x must use `libvtcapture` (video) + `libhalgal` (UI) via `unicapture`, which is a C++ shared-object that `mmap`s the scaler/compositor dumps (`SCALER_OUTPUT / SCALER_INPUT / BLENDED_OUTPUT / OSD_OUTPUT / HISTOGRAM_OUTPUT`) — the quirk bitmask `0x1,0x2,0x4,0x8,0x10,0x20,0x40,0x100` exists because scaler routing differs per SoC/panel, and the CX specifically may need `QUIRK_VTCAPTURE_FORCE_CAPTURE 0x100` (custom kernel module) for protected-path HDMI. The binary cannot run inside Node.js (`Don't use synchronous API`, `"Services should not run for very long periods (minutes) primarily because of the cost of memory"`); it must be `scp`'d to `/media/developer/apps/usr/palm/services/com.ha.tvbridge.service/bin/hyperion-webos` and respawned from `/var/lib/webosbrew/init.d` via `startup.sh`'s `run-parts`, with flatbuffer to `127.0.0.1:19400` (HyperHDR) or `19445` (HyperionNG). The PicCap AI conflict is not advisory — AI Picture Pro / AI Brightness / AI Genre / AI Game Optimizer reuse the same scaler capture pipeline and cause `~200–500 ms dropouts` with LED blackout whenever AI re-analyses the frame; the companion must either detect `com.webos.service.config/getConfigs {"configNames":["com.webos.surfacemanager.ai.*"]}` AI keys and warn, or document `"Deactivate AI service under Settings → General → AI service"` as a prerequisite. Without root + native + AI-off, ambient is a demo that drops frames under load.

*Voice satellite is technically reachable but practically marginal on CX SoC and hinges on mic hardware that the TV does not ship.* The OSE `ai.voice start` path is a dead end (`ai.management`, `only for allowed clients`, plus Google Assistant credential dance that does not map to ThinQ). The viable path is a native daemon that captures PCM via ALSA/UMI (`com.webos.service.audio/listSupportedDevices` shows `usb_mic0 / usb_mic1 / pcm_input`, `master/getMicVolume`, `getSourceStatus sourceType record/btcallsource/alexa/webcall/voiceassistance`) and streams via Wyoming/Assist WS (`sample_rate 16000`, `noise_suppression_level 2`, `auto_gain_dbfs 31`, `volume_multiplier 2.0`). The CX has no far-field array; its only mic is the Magic Remote's BT MEMS (exposed as `sourceType voiceassistance` or `webcall` when the mic button is held, not as continuous `record`). Continuous wake-word detection via `openWakeWord` would therefore require either a USB mic array plugged into the TV (then `usb_mic0` appears) or holding the remote button — both niche. Even with a USB array, on-SoC VAD + Opus encoding at 16 kHz plus flatbuffer capture concurrently will compete for the ~1.2–1.6 GB user-reclaimable RAM before the 250 MB `low.enter` kill; the Assist docs' `wake_word timeout 3s` and `timeout 300s` pipeline window are LAN-friendly but the daemon must handle `wake-word-timeout` and `stt-no-text-recognized` retries without leaking file descriptors. HA reviewers will rightly flag this as "Platinum with caveats" — ship the Wyoming client, but default it to disabled and document `usb_mic0` as a prerequisite.

*Dashboard and camera fill the remaining quadrants.* Lovelace rendering is a pure WebView problem: a `handlesRelaunch:true` Enact app that stays `visibilityChange:hidden` / `suspended` until the user invokes it (Launcher / Recents / `PalmSystem.activate()`), with bundled `assets/` (offline-first per App Resources), `requiredMemory 120–150` (inside the `available 5995 / total 7538` OSE reference envelope, which on the CX 3 GB SoC translates to `~120 MB` being the polite budget before `requireMemory` pressure and `getManagerEvent killing` fires), and `icon 80×80 / largeIcon 130×130 / splashBackground 1920×1080` exactly sized. It does not need root or a native companion, but it does need the JS service's Activity to keep WS state warm while hidden. Camera via `com.webos.service.camera2` is the inverse: it only works with a V4L2 UVC USB camera (`getCameraList` → `[]` on stock CX), but when hardware is present it is a one-line HA camera entity (`capture` to `/tmp/Picture*.jpeg` + file sensor or shared-memory preview) at `ACG camera.operation` (dev-reachable). Without hardware it is an audited absence to document, not a broken promise.

## Committed position

The "ultimate" edge-node is not one monolith but a strict stack with a single must-have, one rooted show-stopper, and two conditional extras: ship HDMI-CEC hub as the stock-feasible, low-RAM, dev-ACLed first deliverable (`requiredPermissions ["cec.query","cec.operation"]`, JS service proxy with foreground+explicit+persist Activity, TV as `0.0.0.0` bridge mapping HA's `hdmi_cec` device tree to `luna://com.webos.service.cec/sendCommand`), then gate the ambient-capture flagship behind a rooted native `hyperion-webos` `unicapture` daemon (`libvtcapture + libhalgal` on webOS 5.x CX, quirks probed as `quirks = 0x1|0x2|0x40|0x100` per panel with `QUIRK_VTCAPTURE_FORCE_CAPTURE` ready for protected HDMI, flatbuffer to `127.0.0.1:19400`, installed to `/media/developer/.../bin/` and respawned from `/var/lib/webosbrew/init.d` via `startup.sh` before `ls-control scan-services`, plus hard prerequisite `Settings → General → AI service → AI Picture Pro/Brightness/Genre/Game Optimizer OFF` or document the 200–500 ms dropout contract), while Lovelace dashboard ships as a suspended-by-default Enact WebView (`handlesRelaunch:true`, `requiredMemory 120`, `icon 80×80 / largeIcon 130×130` exact, bundled `assets/` offline-first, WS state held by the JS service's Activity through `visibilityChange:hidden`) and voice/camera are explicitly conditional — Wyoming satellite only if the user supplies a `usb_mic0` UVC array (CX has no far-field mic; Magic Remote `sourceType voiceassistance` is push-to-talk, not wake-word), streaming 16 kHz PCM via HA `assist_pipeline/run` with `noise_suppression 2 / auto_gain 31 / volume 2.0` and `wake_word timeout 3s`, and camera only via `com.webos.service.camera2` with a plugged UVC camera — because the low-memory killer's `low.enter 250 MB / critical.enter 100 MB` (from `getMemoryStatus` `available 5995 / total 7538` reference) will reap any Enact WebView or long-running JS handler that claims it can do always-on ambient + wake-word + Lovelace on the CX's ~1.2 GB user-reclaimable heap without a native companion, while the documented platform guidance `"Services should not run for very long periods (minutes) primarily because of the cost of memory"` forces the heavy loops out of Node.js into the `init.d` daemon, making the hybrid Enact(hidden) + JS service(keep-alive proxy, thin) + native `init.d` companion the only architecture that survives both the 5-second `No active activities` death and the `memorymanager` `killing` event with the TV's tuner/HDMI compositor still in the foreground.

- **Position:** CEC hub is stock-feasible without native binary; ambient capture is the rooted flagship but requires elevated unicapture native binary + AI Picture off; Lovelace dashboard is an Enact suspended WebView at ~120 MB; voice/camera are USB-hardware-conditional via Wyoming/camera2 and must default off on CX.
- **Confidence:** medium-high (68%) — CEC ACG tiering, unicapture quirks/AI conflict, and memorymanager thresholds are ground truth from OSE + piccap + hyperion-webos; downgraded from high because CX α9 exact free heap under broadcast+HDMI load and whether `libvtcapture` vs `libdile_vt` is primary on 04.40.16 5.4.1 AU require live `ls-monitor -i` + `hyperion-webos --quirks` trial on 10.1.1.209 that the corpus does not instrument.
- **Boundary conditions:** Applies to 2020 α9 Gen3 CX (webOS TV 5.4.1 O20, 3 GB SoC, ~1.2–1.6 GB user-reclaimable) rooted via webosbrew with `/var/lib/webosbrew/startup.sh` + `init.d` + `elevate-service` `all` role; does not apply to unrooted CX (ambient reverts to screenshot-only `tv/executeOneShot`, voice limited to `getAudioEffectsStatus` telemetry), to webOS 3.x (libgm vs libhalgal split and 250→280 low thresholds differ), or to TVs without USB power budget for UVC camera/mic array (camera/voice pillars collapse).
- **What would change this position:** A live `luna-send -i luna://com.webos.service.memorymanager/getMemoryStatus` dump on 10.1.1.209 showing `total` ≠ 7.5 GB reference and `low.enter` far lower than 250 MB (e.g., 120 MB), or a `hyperion-webos` run on the CX with `quirks 0` producing stable 30 fps capture without AI Picture disabled, or a `listSupportedDevices` trace showing a built-in `usb_mic`/`pcm_input` array-mic present without USB hardware plus `com.webos.service.ai.voice` reachable without `ai.management` 401 — any one would promote voice/ambient to stock-feasible and collapse the native-binary requirement.
- **Evidence weight:** 3 canonical OSE service docs support (memorymanager thresholds + killing event, ai.voice management gate, camera2 V4L2-only), 2 field binaries support (hyperion-webos unicapture quirks/AI conflict, piccap elevate-service pattern), 2 HA voice specs support (Wyoming local-push + Assist pipeline WS sample_rate 16000 streaming), 1 lifecycle trio supports dashboard shape (app-resources packaging + visibilityChange suspended + JS FAQ 5s keepAlive); 1 absence weakens CX SoC precision (no instrumented heap/PSS trace on 10.1.1.209 under load).
